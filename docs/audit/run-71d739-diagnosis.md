## 3. Engine defects, ranked

### D1. A universal claim met by a count-0 absence on an empty list

Artifact. The shipped recording (`scenarios[9].steps`, the repair pass's): navigate /category/hand-tools; capture the count of `[data-test='product-name']` (value "9", events line 684); `set_checked` on role checkbox name "Hammer" exact (`elementKey` ending `ul[0]>div[0]>label[0]>input@category_id[0]`); `assert_compare less` on the count (passed, events line 690); `toHaveCount 0` on `[data-test='product-name']:not(:has-text("Hammer"))` (passed 7 ms after the call, events lines 700 and 701); `toBeChecked` on the checkbox. A passing compare's result carries no values, so the shipped recording does not hold the count after the filter. The first pass did the same click on the same page and looked: before it, `get_dom` (events line 115) listed 22 links with 9 product links on page 1 of 3 (seven of them hammer names: "Claw Hammer with Shock Reduction Grip", "Hammer", "Claw Hammer", "Thor Hammer", "Sledgehammer", "Claw Hammer with Fiberglass Handle", "Court Hammer"), 9 Compare buttons and pagination; after it, `get_dom` (events line 139) listed 13 links, all navigation and footer, and 7 buttons, none a Compare or pagination button. The Explorer's own words: "The product list went from 9 to 0" (events line 141) and "Wait ... this is weird that Hammer filter returned 0" (events line 145).

How the absence form was reached. The Critic's first pass asked for the honest form, rule 11's all-items check (events line 611: "An all-items assertion on product names matching 'Hammer' is required"). The repair Explorer tried it and RULE 7 refused it, because "Hammer" was not a value the scenario typed (events line 693; the first pass hit the same refusal at events line 126). A `toHaveText` regex on the whole list could not resolve to one element (events line 697). The Explorer then put the literal inside the selector (`:not(:has-text("Hammer"))`), which RULE 7 does not read: it judges an assertion's expected value, and a count of 0 is allowed. The repair review accepted it: "checks that zero non-Hammer products exist, which is an effective all-items assertion satisfying rule 11" and "the count=0 absence assertion proves only hammers remain" (events line 771).

Consequences: the test passes on an empty list, so R3 ("The category filter narrows the list to products in the selected category") is credited covered by a test that never sees a product of the category; and if the empty Hammer result is a product bug (D6b), the shipped test keeps it green.

Code. `UNIVERSAL_CLAIM_RULE` (`doctrine.ts` line 18, doctrine rule 11, quoted by the Critic's flagging rule 6 at `critic.ts` line 136) names "an all-items assertion ... or a count-0 absence assertion" as equal; only the all-items form "checks in one read of the whole list that there is at least 1 item". `catalogueLiteralReason` (`gate.ts` line 714) reads the assertion's text, value and pattern, never a `:has-text()` argument in a css target. `typedValueForPattern` (`all-items.ts` line 136) accepts a fill or a navigate query value only, never the name of a control the scenario checked.

Fix direction: (a) a count-0 absence backs a universal claim only beside a check, after the last action, that the same list holds at least 1 item; doctrine rule 11 and the Critic's rule 6 say so in the same words. (b) The accessible name of a control the scenario itself clicked or checked (the "Hammer" checkbox) counts as a chosen value for an all-items pattern, as a typed value does, so the honest form can be recorded. (c) RULE 7 reads a literal inside `:has-text()`, `:text()`, `:text-is()` or `text=` in an assertion's css with the rules it applies to an expected value. Lock: a fixture list that empties after a filter click; the absence form alone refused or failing, the all-items form on the checked label failing on the empty list and passing on a list of matching items, in the tool, replay and the emitted spec.
